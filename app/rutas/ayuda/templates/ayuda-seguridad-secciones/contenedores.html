Reactivar el sistema

A. Después de reiniciar o apagar la PC o el servidor
  1. Abrir Docker Desktop (en Windows) y esperar a que diga Engine running. En Linux, Docker arranca solo con el sistema.
  2. Los contenedores vuelven a levantarse solos (restart: always). Comprobar con docker ps --filter name=syscomcli.
  3. Si alguno no aparece, levantar todo: docker compose -f dock/docker-compose.yml up -d.
  4. Entrar a https://localhost e iniciar sesión.
  5. El backup hace una copia apenas arranca: confirmarlo con docker logs syscomcli_backup --tail 5.
B. La página no carga o muestra "502 Bad Gateway"
  1. docker ps -a --filter name=syscomcli: ver qué contenedor no está Up o se reinicia una y otra vez (Restarting).
  2. Leer su log: docker logs <contenedor> --tail 50. El error suele estar en las últimas líneas.
  3. Si es la app y el error es de configuración (por ejemplo SECRET_KEY ausente o password authentication failed), corregir el .env y recrear (capítulo Solución de problemas).
  4. Si no hay un error claro, reiniciar ese contenedor: docker restart <contenedor>.
  5. Si sigue igual, recrearlo: docker compose -f dock/docker-compose.yml up -d --force-recreate <servicio>.
C. La base de datos no arranca
  1. docker logs syscomcli_bd --tail 50.
  2. Si dice No space left on device: liberar espacio en disco (docker system df; borrar imágenes viejas con docker image prune, nunca volúmenes).
  3. Si el log indica datos dañados y no se recupera con un reinicio, hacer la restauración de emergencia (capítulo Backups).
D. Las tareas automáticas no se ejecutan (recordatorios, turnos)

Ver el apartado "Tareas programadas" más abajo. En general alcanza con docker restart syscomcli_app.

E. Instalación nueva desde cero (otra PC u otro servidor)
  1. Instalar Docker (Docker Desktop en Windows; Docker Engine en Linux) y copiar el proyecto.
  2. Crear el .env a partir de .env.example y generar todas las claves nuevas (capítulo Configuración). En el servidor: SESSION_COOKIE_SECURE=1 y FLASK_DEBUG=0.
  3. Generar el certificado de HTTPS (capítulo HTTPS): autofirmado en desarrollo, Let's Encrypt en el servidor.
  4. Comprobar que exista dock/backup/keys/backup_pub.asc (la clave pública del backup).
  5. Levantar solo la base: docker compose -f dock/docker-compose.yml up -d db. Al ser un volumen nuevo, crea el usuario postgres con la contraseña del .env.
  6. Crear la base de trabajo y el rol de la aplicación: 
    docker exec syscomcli_bd psql -U postgres -c "CREATE DATABASE sysclin_bd"
$appPwd = (Select-String -Path .env -Pattern '^DB_PASSWORD=(.*)$').Matches[0].Groups[1].Value
Get-Content migrations\17_rol_sysclin_app.sql -Raw | docker exec -i syscomcli_bd psql -U postgres -d sysclin_bd -v ON_ERROR_STOP=1 -v "app_password=$appPwd" -q
  7. Cargar los datos desde el último backup con la restauración de emergencia (capítulo Backups, pasos 4 y siguientes).
  8. Volver a ejecutar el script 17 de migrations/ (mismo comando del paso 6), para que los permisos de sysclin_app queden completos.
  9. Levantar todo: docker compose -f dock/docker-compose.yml up -d (en el servidor, con los dos archivos).
  10. Hacer el chequeo periódico completo (Manual de seguridad, capítulo «Auditoría y chequeo periódico»).

Modo de arranque de la aplicación

El contenedor syscomcli_app arranca de una de dos formas, según FLASK_DEBUG del .env:

FLASK_DEBUGArranca conPara
1Servidor de desarrollo de Flask + debugpy (puerto 5678), con recarga automática al guardar códigoDesarrollo
0gunicorn: 1 proceso con 8 hilos y un límite de 120 s por peticiónServidor

En el servidor se usa un solo proceso a propósito: las tareas programadas arrancan una vez por proceso y, con más procesos, los recordatorios se enviarían repetidos.

Ver en qué modo está corriendo:

docker exec syscomcli_app sh -c "cat /proc/1/cmdline | tr '\0' ' '"

Se espera python -m debugpy ... run.py en desarrollo y gunicorn --bind 0.0.0.0:5000 --workers 1 --threads 8 ... en el servidor.

Tareas programadas

Los recordatorios por WhatsApp, la extensión de turnos de agenda y la limpieza de sesiones corren dentro de la app, en un único proceso. Lo garantiza un candado en PostgreSQL (advisory lock 7420001): el proceso que lo toma ejecuta las tareas; cualquier otro lo avisa en el log y no las arranca.

Ver quién ejecuta las tareas (debe haber exactamente una fila):

docker exec syscomcli_bd psql -U postgres -d sysclin_bd -Atc "SELECT l.pid, a.usename, host(a.client_addr) FROM pg_locks l JOIN pg_stat_activity a ON a.pid=l.pid WHERE l.locktype='advisory' AND l.objid=7420001"
  • Ninguna fila: ningún proceso ejecuta las tareas. Reiniciar la app: docker restart syscomcli_app.
  • Ver los arranques en el log: docker logs syscomcli_app --since 1h 2>&1 | Select-String 'Scheduler iniciado|NO iniciadas'.
